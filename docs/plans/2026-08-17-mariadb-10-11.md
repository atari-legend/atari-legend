# Move the development stack to MariaDB 10.11 LTS

*2026-08-17*

## Why

The Docker Compose environment ([docker-environment], the parent of this repo)
ran `mysql:5.7.44`, end of life since October 2023. Development moves to
**MariaDB 10.11 LTS**, and CI with it: the CI service image was pinned to the
same 5.7 image on purpose, "so CI cannot disagree with it on server behaviour",
and that property is worth keeping.

[docker-environment]: https://github.com/atari-legend/docker-environment

## What changed

### docker-environment

- `docker-compose.yml`: the database service runs `mariadb:10.11` and is renamed
  from `mysql` to `db`, engine-neutral for whatever comes next — so `DB_HOST=db`
  now, in every `.env`. Its variables are the image's own `MARIADB_*`. The
  service gained a healthcheck (`healthcheck.sh --connect --innodb_initialized`),
  and `artisan` now waits for `service_healthy` rather than for the container to
  merely exist, because that is the container migrations run in.
- `mysqld.cnf`: `NO_AUTO_CREATE_USER` dropped from `sql-mode`. It became a no-op
  after MySQL 5.7; 10.11 still accepts it, but MySQL 8 and MariaDB 11 refuse to
  start with it listed. The rest stays, so `ONLY_FULL_GROUP_BY` stays out for the
  clients that do not set their own mode — which is the legacy CPANEL, not the
  site.
- `README.md`: names the server, points at `DB_HOST=db` and
  `DB_CONNECTION=mariadb`, and spells out that the service holds no volume.

### This repo

- `.env.example` and `tests/e2e/README.md`: `DB_CONNECTION=mariadb`, which selects
  the `mariadb` connection `config/database.php` already carried, and `DB_HOST=db`
  for the renamed service. `CLAUDE.md` names the server.
- `.github/workflows/build-and-deploy.yml`: `mariadb:10.11` service, named `db`
  like in Compose, with `MARIADB_*` env and the image's own healthcheck script.
  The "Match the development MySQL configuration" step is gone: it set a *global*
  sql_mode, and every client in CI is Laravel, which sets its own session mode
  regardless. It also depended on a `mysql` binary being on the runner, which the
  ubuntu-24.04 image does not promise.

Two things the switch broke, both fixed here:

- **`ONLY_FULL_GROUP_BY`.** MySQL 5.7 resolves a grouped query when the selected
  columns are functionally dependent on the grouping key; MariaDB does not
  implement that analysis, so the home page 500s on `pub_dev_name` grouped by
  `pub_dev_id`. Laravel's `'strict' => true` sets that mode per session whatever
  the server config says, so `mysqld.cnf` leaving it out changes nothing for the
  app. Rather than weaken the connection, the offending queries were fixed: the
  four `Cards\Tops` queries and the menu set list now group by the name as well
  as the key it depends on, and `Cards\TopGames` aggregates the votes in a
  subquery instead of selecting `game.*` alongside aggregates. `strict` stays
  true, and the whole strict list — `ONLY_FULL_GROUP_BY` included — applies.
  `AdminStatisticsHelper` already grouped by key *and* label everywhere, so it
  needed nothing.
- **`getDriverName() === 'mysql'` guards.** The driver name is now `mariadb`, so
  four migrations silently skipped their DDL: the `sndhs` `FULLTEXT` index (which
  the admin game-music search needs for `MATCH ... AGAINST`), the
  `news_search_wordlist` key and `AUTO_INCREMENT`, ten menu table comments, and a
  news-text `regexp` rewrite. They now test `!== 'sqlite'`, which is both what
  they meant and the convention the newer migrations already follow.

## Notes

The local database is deliberately ephemeral: the `db` service has no volume,
its data lives in the container layer, and a 5.7 data directory could not have
been read by MariaDB anyway (a cross-engine move needs a logical dump). Rebuild
the schema with `docker compose run --rm artisan migrate:fresh`, then restore a
dump, or seed the E2E fixture with `db:seed --class=E2ESeeder`. Not the default
`DatabaseSeeder` — it predates this schema and inserts a `users.name` that does
not exist, on MariaDB and MySQL alike.

Nothing in the schema is driver-sensitive, so `mysql` → `mariadb` is a label
change: there are no `uuid`/`json` columns where Laravel's MariaDB grammar
differs, the only raw DDL is an ENUM `MODIFY`, an `AUTO_INCREMENT MODIFY`, table
comments and `ALTER TABLE sndhs ADD FULLTEXT title_search (title)` (InnoDB
fulltext, supported), and no raw SQL uses a reserved word unquoted. The PHPUnit
suite runs on SQLite and is unaffected. The legacy CPANEL (PHP 8.4 + mysqli)
shares the server and keeps working — MariaDB still offers
`mysql_native_password`.

Worth remembering: `mysqld.cnf` only governs the clients that do not pick their
own mode — CPANEL, phpMyAdmin, the CLI. Laravel picks its own in
`MySqlConnector::getSqlMode()` (and the `MariaDbConnector` override), so the
site's behaviour is decided by `'strict' => true` in `config/database.php`, not
by the server.

Checked before this landed, against MariaDB 10.11 with the full strict session
mode: the 262 migrations from scratch, the PHPUnit suite on SQLite (986 passing),
and the whole Playwright suite (319 passing), which includes the admin statistics
page — the heaviest grouped queries in the app.

**The servers have not moved.** dev.atarilegend.com and www.atarilegend.com are
out of scope here, so CI now validates migrations against MariaDB while
production still runs MySQL 5.7. Do not adopt MariaDB-only DDL in migrations
until they move — in particular `ALTER TABLE ... RENAME COLUMN`, whose absence
in 5.7 shapes the primary-key rename plan.
