# Move to MariaDB 10.11 LTS

*2026-08-17*

## Why

Development and CI ran MySQL 5.7.44, end of life since October 2023. Both move
to **MariaDB 10.11 LTS**. CI had been pinned to the same 5.7 image the
development environment used, on purpose — "so CI cannot disagree with it on
server behaviour" — so the two had to move together.

## What changed

- `.env.example` and `tests/e2e/README.md`: `DB_CONNECTION=mariadb`, which
  selects the `mariadb` connection `config/database.php` already carried, and
  `DB_HOST=db` for the renamed database service. `CLAUDE.md` names the server.
- `.github/workflows/build-and-deploy.yml`: a `mariadb:10.11` service named `db`,
  with `MARIADB_*` env and the image's own healthcheck script
  (`healthcheck.sh --connect --innodb_initialized`). The "Match the development
  MySQL configuration" step is gone: it set a *global* `sql_mode`, and every
  client in CI is Laravel, which sets its own session mode regardless. It also
  depended on a `mysql` binary being on the runner, which the ubuntu-24.04 image
  does not promise.

Two things the switch broke, both fixed here:

- **`ONLY_FULL_GROUP_BY`.** MySQL 5.7 resolves a grouped query when the selected
  columns are functionally dependent on the grouping key; MariaDB does not
  implement that analysis, so the home page 500s on `pub_dev_name` grouped by
  `pub_dev_id`. Laravel's `'strict' => true` sets that mode per session whatever
  the server is configured with, so this was never something the server config
  could settle. Rather than weaken the connection, the offending queries were
  fixed: the four `Cards\Tops` queries and the menu set list now group by the
  name as well as the key it depends on, and `Cards\TopGames` aggregates the
  votes in a subquery instead of selecting `game.*` alongside aggregates.
  `strict` stays true, and the whole strict list — `ONLY_FULL_GROUP_BY` included
  — applies. `AdminStatisticsHelper` already grouped by key *and* label
  everywhere, so it needed nothing.
- **`getDriverName() === 'mysql'` guards.** The driver name is now `mariadb`, so
  four migrations silently skipped their DDL: the `sndhs` `FULLTEXT` index (which
  the admin game-music search needs for `MATCH ... AGAINST`), the
  `news_search_wordlist` key and `AUTO_INCREMENT`, ten menu table comments, and a
  news-text `regexp` rewrite. They now test `!== 'sqlite'`, which is both what
  they meant and the convention the newer migrations already follow.

## Notes

A 5.7 data directory cannot be read by MariaDB — a cross-engine move needs a
logical dump — so the local database is rebuilt rather than migrated. Run
`docker compose run --rm artisan migrate:fresh`, then restore a dump, or seed the
E2E fixture with `db:seed --class=E2ESeeder`. Not the default `DatabaseSeeder` —
it predates this schema and inserts a `users.name` that does not exist, on
MariaDB and MySQL alike.

Nothing in the schema is driver-sensitive, so `mysql` → `mariadb` is a label
change: there are no `uuid`/`json` columns where Laravel's MariaDB grammar
differs, the only raw DDL is an ENUM `MODIFY`, an `AUTO_INCREMENT MODIFY`, table
comments and `ALTER TABLE sndhs ADD FULLTEXT title_search (title)` (InnoDB
fulltext, supported), and no raw SQL uses a reserved word unquoted. The PHPUnit
suite runs on SQLite and is unaffected. The legacy CPANEL (PHP 8.4 + mysqli)
shares the database and keeps working — MariaDB still offers
`mysql_native_password`.

Worth remembering: the server's configured `sql_mode` only governs clients that
do not pick their own — CPANEL, phpMyAdmin, the CLI. Laravel picks its own in
`MySqlConnector::getSqlMode()` (and the `MariaDbConnector` override), so this
site's behaviour is decided by `'strict' => true` in `config/database.php`, not
by the server.

Checked before this landed, against MariaDB 10.11 with the full strict session
mode: the 262 migrations from scratch, the PHPUnit suite on SQLite (986 passing),
and the whole Playwright suite (319 passing), which includes the admin statistics
page — the heaviest grouped queries in the app.

**The servers have moved too.** dev.atarilegend.com and www.atarilegend.com now
run MariaDB 10.11, so development, CI and both deployments agree on the server.
MariaDB-only DDL is therefore available to migrations — in particular
`ALTER TABLE ... RENAME COLUMN`, absent from 5.7, which is what makes the
[primary-key rename](2026-08-17-primary-key-rename.md) cheap enough to be worth
doing table by table.
